# 项目实施与迁移计划

| 属性 | 内容 |
|---|---|
| 版本 | `0.2` |
| 状态 | 待评审 |
| 实施策略 | 本机副本验证 → 阿里云测试环境 → 迁移演练 → 正式切换 |

## 1. 实施原则

- 先固定业务行为测试，再改数据库访问。
- 每一阶段都有可验证交付物和退出条件。
- 任何演练不直接改生产主库。
- 切换前始终以 SQLite 为唯一生产主库。
- 切换后始终以 RDS MySQL 为唯一生产主库。
- 每个功能继续复用现有质量门，并提交 Git。

## 2. 阶段与交付物

### Phase 0：基线与决策门

任务：

1. 批准 PRD、架构、Agent 护栏和验收标准。
2. 盘点 SQLite schema、触发器、FTS5、SQL 方言和事务调用。
3. 为现有判题、推荐、审核、复习和 PDF 建立行为基线。
4. 确认阿里云地域、域名、备案、RDS 系列和模型预算。
5. 确认租户、角色、邀请、监护关系、隐私同意和数据保留边界。

退出条件：所有未决事项有负责人和决策时点；不得带着数据库语义未知项进入迁移开发。

### Phase 1：数据访问与 MySQL 兼容

任务：

1. 将数据库连接配置收敛到唯一入口。
2. 建立 MySQL 8.0 schema 和迁移版本管理。
3. 映射 SQLite 与 MySQL 的类型、约束、自增、upsert 和时间语义。
4. 将 FTS5 检索映射到 MySQL ngram FULLTEXT，并保留推荐的结构化过滤与排序。
5. 在临时 MySQL 中运行完整业务回归。
6. 新增租户与成员关系表，为私人业务表补齐 `tenant_id`/`student_id`、复合索引和约束。
7. 将现有李兆霖数据迁入唯一的种子家庭租户，公共已验证题库保持 `global` 范围。

退出条件：同一固定数据集在 SQLite 基线和 MySQL 上产生等价的业务结果；所有差异有书面说明。

### Phase 2：本机 Web MVP

任务：

1. 建立服务端页面、登录与角色授权。
2. 实现邀请、当前租户切换、监护人—学生绑定和账号停用。
3. 实现任务创建、状态查询和异常展示。
4. 接通照片判题、错题详情、推荐、每日复习和 PDF。
5. 建立 Agent Gateway、Schema 校验、幂等、租户预算和审计。
6. 使用至少两个隔离租户的脱敏数据库副本完成端到端测试。

退出条件：PRD 中的学生与家长主流程全部通过，不连接生产主库。

### Phase 3：阿里云测试环境

任务：

1. 部署 ECS、RDS MySQL、私有 OSS、HTTPS 和最小权限网络。
2. 配置测试域名、密钥、日志、告警和备份。
3. 验证对象上传、模型调用、数据库连接和 PDF 下载。
4. 完成 Agent 越权、提示词注入、重复提交和故障恢复测试。
5. 完成跨租户访问、邀请劫持、对象越权、队列公平性和临时支持访问测试。

退出条件：安全与运维验收通过；RDS 不通过公网暴露。

### Phase 4：迁移演练

任务：

1. 从 SQLite 一致性备份生成迁移输入。
2. 导入测试 RDS，重建约束、索引和全文索引。
3. 比较表数、行数、主键、外键、关键字段哈希和业务统计。
4. 抽查题干、答案、解析、来源、审核、错题、复习、推荐和作答链。
5. 演练回滚和重新迁移。

退出条件：迁移报告无未解释差异，恢复演练成功。

### Phase 5：正式切换

任务：

1. 公告维护窗口并停止 SQLite 新写入。
2. 执行最终 SQLite 健康检查和加密备份。
3. 增量或全量迁移到生产 RDS。
4. 执行自动校验与人工抽查。
5. 切换应用数据库连接并进行冒烟测试。
6. 观察稳定后关闭旧写入口；SQLite 保留为只读归档。

退出条件：Web 生产流量只写 RDS；不存在第二个活动主库。

### Phase 6：稳定与后续

任务：

1. 复盘故障、时延、模型成本和用户反馈。
2. 评估是否 Web 化管理端导入和审核。
3. 只有指标证明必要时，依次评估多 Worker、ALB/多 Web 实例、Redis/消息队列或独立对象处理。
4. 教师、班级、学校租户、计费与开放注册作为独立后续产品决策，不与稳定性优化混合实施。

## 3. SQLite → MySQL 映射清单

| SQLite 能力 | MySQL 目标 |
|---|---|
| `INTEGER PRIMARY KEY`/自增 | `BIGINT AUTO_INCREMENT` 或保留文本业务 ID |
| `INSERT OR IGNORE` | `INSERT IGNORE` 或显式唯一键冲突处理 |
| `ON CONFLICT ... DO UPDATE` | `ON DUPLICATE KEY UPDATE`，逐语句核验语义 |
| 动态类型 | 明确 `VARCHAR/TEXT/JSON/DECIMAL/DATETIME/BOOLEAN` |
| FTS5 trigram | InnoDB FULLTEXT + ngram parser |
| SQLite 触发器 | MySQL 触发器或应用层事务；优先保留单一业务入口 |
| SQLite 文件备份 | RDS 自动备份 + 逻辑导出 + 恢复演练 |

不得进行简单字符串替换式迁移；每种 SQL 语义必须有测试覆盖。

## 4. 正式迁移校验

必须同时检查：

- 每张表行数。
- 主键集合与唯一约束。
- 外键孤儿记录为零。
- 题库题干、答案、解析、来源和验证状态哈希。
- `verified` 数量、未验证数量和审核记录数量。
- 错题、复习阶段、推荐和作答关系。
- 推荐结果中不存在未验证题。
- MySQL 中文搜索和现有关键查询的结果质量。
- 对象键与 OSS 对象完整对应。
- 每条私人记录均归属种子租户与正确学生；公共题库范围和租户私有范围无混淆。

## 5. 回滚方案

正式切换失败时：

1. 立即停止 Web 写入。
2. 保留失败 RDS 实例和日志用于取证，不继续修补生产数据。
3. 若切换后尚无有效新写入，恢复旧 SQLite 服务。
4. 若已有有效新写入，禁止直接双向合并；进入人工决策并使用审计日志构建受控补偿。
5. 修复迁移工具后从已验证快照重新演练。

回滚能力必须在正式切换前演练，而不是故障发生后首次执行。

## 8. Git 与变更管理

- 每个实施任务使用 `codex/` 前缀分支，除非项目发起人另有要求。
- 代码、迁移、测试和受影响文档在同一变更中提交。
- 生产数据、密钥、照片、试卷原件和生成 PDF 不进入 Git。
- 数据库 schema 迁移必须单向编号、可审计，并提供恢复说明。
- 未通过相应阶段退出条件的代码不得标记为已完成。
